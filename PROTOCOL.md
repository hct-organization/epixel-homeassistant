# ePiXeL ⇄ Home Assistant — Local Protocol Contract

**Version 2** · This document is the single source of truth for **both** the
Python integration and the display firmware. If one side needs to change,
this file changes first.

> **Changes from version 1** — a `dim` box type for lights that can be set to a
> level rather than only switched, three new commands to drive it, two more
> icons (`dimmer`, `switch`), a per-entity icon override chosen by the user,
> and a stated guarantee about the text the device receives. A version 1 device
> ignores what it does not recognise and keeps working.

## Overview

| | |
|---|---|
| Transport | HTTP/1.1, **local network only**, plain HTTP (no TLS) |
| Direction | **Always device → Home Assistant.** The device opens no listening port |
| Body | JSON, UTF-8 |
| Auth | `X-EPX-Token: <token>` on every endpoint except `ping` and `pair` |
| Base | `http://<ha-host>:<port>/api/epixel` |

The device locates Home Assistant over **mDNS**: `_home-assistant._tcp.local.`

### Why single-letter field names

The device parses JSON into a small PSRAM buffer. Long field names would triple
the payload for no gain. The meaning is documented here, so the abbreviation is
safe.

---

## 1. `GET /ping` — discovery

No auth. Answers exactly one question: "is the ePiXeL integration installed here?"

```json
{ "epixel": 1, "ver": 1, "hass": "2026.7.4" }
```

`404` → not installed. The device then shows installation instructions.

---

## 2. `POST /pair` — pairing

No auth. Called **every 2 seconds** while the pairing screen is open.

```json
{ "pin": "4729", "name": "ePiXeL Display", "session": "9f3a1c72" }
```

- `pin` — 4 digits, generated by the device and shown on its screen
- `session` — random 8 hex generated by the device; the token is returned **only
  to the same session**
- `name` — label shown in Home Assistant. The device's **real identity
  (`EPX_…`) is never sent**

**Responses**

| Status | Body | Meaning |
|---|---|---|
| 200 | `{"status":"waiting"}` | request registered, awaiting approval in Home Assistant |
| 200 | `{"status":"paired","token":"…","hass_name":"Home"}` | approved — the device stores the token and stops calling `pair` |
| 429 | `{"status":"busy"}` | more than 3 pending requests; the device backs off 10 s |

**Safeguards (all three together):** a **180 s** window · at most **5 attempts**
· at most **3 pending requests**. Four digits are sufficient *because of* this
combination — the person approving is a logged-in Home Assistant administrator
typing the code from their own screen, which an attacker cannot see.

### First pairing: expect 404 until the dialog is open

Home Assistant does not run an integration's `async_setup` until a config entry
exists, so on a fresh install the endpoints do not exist yet. The integration
brings them up as soon as the user opens **Add Integration → ePiXeL**.

Consequences for the device:

- A `404` on `ping` or `pair` does **not** mean "the integration is missing".
  The device must say *"open Add Integration → ePiXeL in Home Assistant"* — a
  message that is correct whether the integration is absent or merely not yet
  loaded.
- The device must **keep retrying** rather than give up on the first 404.
- This applies only to the first pairing. Once an entry exists, `async_setup`
  runs on every Home Assistant start and the endpoints are always up.

## 3. `GET /view` — everything

Pages, boxes and current values in **one document**. The device knows nothing else.

`GET /view?rev=412&wait=25`

- `rev` — the revision the device already holds. The request is held open for
  `wait` seconds (long poll) and returns **immediately** on any change.
- `wait=0` returns at once. `wait` is capped at 55.

```json
{
  "rev": 413,
  "pages": [
    { "t": "Living room", "b": [
      { "k":"a1b2c3", "n":"Ceiling light", "y":"dim", "v":60,     "i":"dimmer" },
      { "k":"d4e5f6", "n":"Temperature",   "y":"num", "v":"22.4", "u":"°C", "i":"temp", "g":1 },
      { "k":"7a8b9c", "n":"Front door",    "y":"bin", "v":0,      "i":"door" },
      { "k":"0d1e2f", "n":"Desk socket",   "y":"sw",  "v":0,      "i":"plug" }
    ]}
  ]
}
```

| Field | Meaning |
|---|---|
| `k` | opaque key (short digest of the entity_id). **`entity_id` never reaches the device.** Commands and chart requests carry this back |
| `n` | display name, **max 22 characters** |
| `y` | box type, see below |
| `v` | value, meaning depends on `y` |
| `u` | unit, when present (`num` only) |
| `i` | icon name from the **fixed list below**. Unknown → `dot` |
| `g` | `1` when this box has a chart |

### Box types

| `y` | `v` | Interaction |
|---|---|---|
| `sw` | `1` / `0` | Touch toggles it |
| `dim` | `0`–`100` (percent; `0` is off) | Touch toggles, a level control sets it |
| `bin` | `1` / `0` | Read-only |
| `num` | string number, with `u` | Read-only; opens a chart when `g` is set |
| `txt` | string | Read-only |

A device that does not recognise a type must render it read-only rather than
drop the box — the user placed it there and an empty slot reads as a fault.

### Guarantees about `k` and `n`

These two carry different weight and must not be confused.

- **`k` is the machine identifier.** Exactly six characters, `[0-9a-f]` only.
  No spaces, no accents, no punctuation, stable for as long as the entity
  exists. Safe to use in a log line, a filename or a lookup key.
- **`n` is for the human, and only for the human.** The integration
  normalises it before sending: Unicode NFC, control characters and line
  breaks replaced by spaces, runs of whitespace collapsed, ends trimmed,
  then cut to 22 characters. It may still contain spaces and any script the
  user's language uses. **Never derive an identifier from it.**

Where truncation would make two boxes on one page identical, the integration
keeps both ends of the longer name instead (`VitrinLedl…LED Şerit 1`), so the
user is never shown two boxes they cannot tell apart.

**Rules**
- At most **6** boxes per page, at most **8** pages
- Box count picks the layout: **2** → 1×2 · **3–4** → 2×2 · **5–6** → 2×3
- `"pages": []` → the device **removes the Home Assistant page from its
  carousel** (it never shows an empty page)
- A deleted or unavailable entity still returns a box, as `"y":"txt","v":"—"`

## 4. `POST /cmd` — control

```json
{ "k": "a1b2c3", "a": "toggle" }
{ "k": "a1b2c3", "a": "set", "p": 40 }
```

| `a` | Applies to | Effect |
|---|---|---|
| `toggle` | `sw` | Invert |
| `on` / `off` | `sw` | Set explicitly |
| `set` | `dim` | Go to `p` percent (0–100) |
| `up` / `down` | `dim` | Move ten percent from **the light's current level** |

```json
{ "ok": true,  "v": 40 }
{ "ok": false, "e": "entity_not_found" }
```

`v` in the reply is the level the entity actually reached, so the device can
correct itself without waiting for the next `/view`.

Error codes: `entity_not_found` · `not_switchable` · `not_dimmable` ·
`bad_action` · `bad_level` · `service_failed` · `unauthorized`

**Two rules for dimming**

- `up` and `down` are resolved against the light's **live** level, not against
  whatever the device last displayed. A light someone changed at a wall switch
  would otherwise jump to the wrong value on the first press.
- A target under **5 percent** turns the light **off** rather than setting a
  level nobody can see. Sending 2 percent leaves a lamp that looks off but
  reports on, and the next press then climbs from 2 instead of from zero.

The device updates its UI **optimistically before sending**; on `ok:false` it
**reverts and tells the user why**.

## 5. `GET /history` — charts

`GET /history?k=d4e5f6&h=24`

```json
{ "k":"d4e5f6", "u":"°C", "min":18.1, "max":24.7, "n":60,
  "p":[181,183,186,190, ...] }
```

- `p` — **60 points**, values ×10 as integers. About 400 bytes total
- Downsampling happens **on the server**; the device never sees raw history
- A box without a chart returns `{"e":"no_history"}`

---

## 6. `POST /announce` — the display says where to reach it

This is where the direction reverses. Everything above is the device calling
Home Assistant. After announcing, Home Assistant calls the device: the moment a
tracked entity changes, the new `/view` document goes straight to the screen and
the device stops asking.

**Why this exists.** Polling put twenty round trips a minute on the wire for a
screen that usually has nothing new on it, and the constrained side of that
exchange was never Home Assistant — it was the device, whose HTTP work shares
one task with firmware updates, time sync and its own cloud link.

**Why not MQTT.** A broker on the user's network is the industry answer and was
the obvious first choice. It was measured and rejected: a second MQTT client on
the device needs 16 KB of *contiguous internal* SRAM, and the largest free block
is 27.6 KB. Taking more than half of it returns to the conditions of a fault
that once left devices unable to start MQTT at all. This listener costs about
4 KB and asks the user to install nothing.

Request (device -> Home Assistant), authenticated with the pairing token:

```json
{ "ip": "192.168.1.42", "port": 8377, "secret": "9f3c1a7e5b2d4086" }
```

| field | meaning |
| --- | --- |
| `ip` | the device's own address. **Must be private**; anything else is refused, so this endpoint cannot be used to make Home Assistant reach hosts the caller cannot. |
| `port` | where the device listens |
| `secret` | generated by the DEVICE, returned on every push. The direction of trust flips here: until now Home Assistant was proving itself to the device; from now on the device has to check that a push really came from Home Assistant. |

Answer: `{"ok": true}`, or 401 when the token is wrong, 400 for a non-private
address or a malformed target.

**Repeat it.** The device re-announces about once a minute. Its address comes
from DHCP and can change without warning, and a push to a stale address fails
*silently* — the screen would simply stop updating with nothing on it to say
why. Re-announcing turns that from permanent into self-healing.

## 7. `POST http://<device>:<port>/push` — Home Assistant to the display

The only request that travels in this direction. Body is exactly the `/view`
document of section 3, so both sides run one parser and one format.

Header `X-EPX-Push: <secret>` — the value from `/announce`. The device also
checks that the packet came from the paired Home Assistant's address. A request
failing either check is refused **before its body is read**: an endpoint open on
the network must not let an unverified caller decide how much memory to allocate.

Answer: `{"ok": true}`, or 401.

Home Assistant waits about 250 ms before sending, so that a scene switching six
lights becomes one packet carrying the final state rather than six.

**Polling does not go away.** With push working the device asks only when it has
heard nothing for 90 seconds. Push depends on an address that can change and on
a Home Assistant that can restart; both fail by going quiet, which is the
hardest failure to notice. Measuring the silence is what makes it recoverable.

## Not part of the device protocol: `GET /preview`

`GET /preview?k=<key>` returns an HTML page showing the configured pages drawn
at the display's real resolution. **The display never calls this** — it exists
so the person building a page can see the result without walking over to the
screen.

It renders from the same `build_view` the device consumes, so what it shows is
what the device receives; only the paint is reproduced separately.

The page carries entity names and current states, so it is not public. The key
is minted each time the options flow is opened, is valid for one hour, and
replaces the previous one — a link pasted somewhere stops working instead of
lingering.

## Icon list (fixed, 34 names)

```
dot     bulb    dimmer  switch  plug    temp    hum     power
energy  battery motion  door    window  lock    water   fire
gas     co2     lux     press   fan     wind    rain    signal
clock   person  tv      music   cool    heat    valve   sun
moon    shield
```

The shapes are **Material Design Icons** — the same family Home Assistant
itself uses — so an icon on the display matches the one beside the entity in
Home Assistant. They live in `custom_components/epixel/icon_paths.py` together
with their upstream names.

**The display's assets are generated from that same file.** The firmware
repository runs `tools/gen_ha_icons.sh`, which reads `icon_paths.py`, renders
each path and emits the on-device image. The browser preview and the hardware
therefore draw from one source and cannot drift apart — an icon that looks
right in the preview is the icon the display shows.

**How an icon is chosen**

1. If the user picked one for that entity, it wins.
2. Otherwise: a light that reports a brightness capability gets `dimmer`, any
   other light `bulb`.
3. Otherwise: `device_class`, then unit of measurement, then domain.
4. Otherwise `dot`.

A stored choice that is not in the list above is discarded and step 2 runs
instead — a name left over from an older release, or a hand-edited backup,
must never reach the device and draw an empty square.

**To grow this list:** add the glyph to the device font first, then start
emitting the new name. The reverse order draws empty squares on the screen.

## Failure handling

| Situation | Home Assistant | Device behaviour |
|---|---|---|
| Invalid token | `401` | "Access revoked — pair again" + pairing screen |
| Integration missing | `404` on ping | "Home Assistant integration not found" |
| Home Assistant unreachable | — | exponential backoff, capped at 5 min; after 15 min the page leaves the carousel |
| Home Assistant IP changed | — | rediscovered over mDNS, silently |
| 5 consecutive failures | — | drops to a 60 s slow poll, recovers automatically |

**Poll cadence:** page visible → `wait=25` · page not visible → `wait=0` every
60 s · not paired → **no traffic at all**.

## Privacy commitments

- Home data (entity names, states, history) **never reaches the ePiXeL cloud.**
  Device telemetry carries counters only: `ha_ent` · `ha_fail` · `ha_rtt`.
- The device's cloud credentials (JWT / master secret / MQTT password) **never
  travel on this path.**
- The device's real identity (`EPX_…`) **is never sent to Home Assistant.**
- The device connects to **private IP addresses only**; public addresses are
  refused.
- The integration exposes only the entities the user selected — the display
  cannot see the rest of the home.

**Honest limitation:** this is plain HTTP on the local network, so someone able
to sniff that network could capture the token. Accepted because Wi-Fi is already
encrypted by WPA2, the token's authority is limited to the selected entities,
and the user can revoke it at any time.
